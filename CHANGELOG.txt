HDR FLAG: FOLLOW THE SOURCE BY DEFAULT

  --hdr-flag auto|on|off (CLI --fpkg-hdr-flag; Pack dialog → Edit… →
  Retail options). "auto" leaves param.json attribute bit 29 exactly as
  the source declares it — that is the publisher's intent, and the one
  source seen without it belongs to a title whose store page and reviews
  list no HDR support, so forcing the bit only made the console switch
  its output mode. "on" sets the bit, "off" clears it. The console
  follows the bit when set to "HDR when supported"; nothing about it is
  launch-critical. 1.1.12/1.1.13 forced it on for every retail source;
  a remembered setting from those versions migrates to "auto".

RETAIL fPKG BUILDS LAUNCH ON THE CONSOLE

  A retail title built from its own .ffpfsc container installs and
  launches on a retail PS5 (FW 11.60, kstuff-lite 1.13): HDR10, existing
  saves intact. A/B builds on the console isolated what matters; the tool
  now does all of it by default.

  PLAYGO METADATA IS VALIDATED. Some containers carry sce_sys/playgo-*.dat
    with unusable contents. LibProsperoPkg only counts the three files
    ("complete prepared set found; its layout will be preserved") and
    stores them verbatim as CNT entries 0x1001/0x2010/0x2011, which the
    console parses at launch: install fine, icon fine, CE-100022-5. The
    builder now checks each file against its on-wire format (plgx magic
    + size field; \x7fFLT hash table with 56 + table = length; FICM with
    16 + payload = length) and regenerates a consistent set from the
    actual inner tree when any file fails; sce_sys/*.json that is not
    JSON is dropped. --regen-playgo forces regeneration of a valid set.

  RETAIL NORMALIZE (default on; --no-retail-normalize to skip)
    · drm_type=16 in the CNT header for a "standard" Application (upstream
      hard-codes 0; retail packages carry 16). IL patch to
      LibProsperoPkg.dll, so applicationDrmType stays "standard".
    · fakelib/libSceAmpr.sprx and libScePlayGo.sprx are kept. Upstream
      removes exactly these two (FilterFakeLibraryDirectory); they are the
      emulator libraries a backported title relies on. Second IL patch.
    · Valid license.dat/license.info CNT entries via LibProsperoPkg's own
      BuildDebugLicense. Placeholder bytes were dropped silently, which
      leaves a padlock on the homescreen.
    · Retail SELF flavour (ProgramType bit 0x10000000, SELF header byte
      0x0B) on eboot.bin and every prx/sprx; older fake-signers stamp the
      dev flavour. sce_sys/about/*.sprx is left alone.
    · param.json attribute bit 29 = HDR support (--hdr-flag, default on).
      Without it a console on "HDR when supported" runs the title in SDR.
      A "kernel" block is added when the source has none — not
      launch-critical, kept to match retail packages.

  KEYSTONE IS THE SAVE-DATA KEY. sce_sys/keystone is always preserved from
    the source. A build with a regenerated keystone reported every
    existing save as corrupt.

  STORED / AUTOMATIC KRAKEN BACKENDS DO NOT LAUNCH. --kraken-backend
    uncompressed installs but fails with CE-100096-6. The tool warns; the
    app never sends it. The default inner codec layer is now "kraken" —
    the configuration every launching build used ("none" is untested on
    the console).

  Plumbing: --help documents every flag; CLI and app pass the switches
    through (--fpkg-no-retail-normalize, --fpkg-no-hdr-flag,
    --fpkg-regen-playgo, --fpkg-no-fake-sign); the Pack dialog exposes them
    under Edit… with launchable defaults.

  The DLL patches are reproducible: patches/CecilPatch (Mono.Cecil) applies
    both to a pristine LibProsperoPkg 1.2.0 by instruction pattern and is
    idempotent. See backend/native/src/ffpfsc-pkg-tool/patches/README.md.

RETAIL-PERFECT fPKG BUILDS OUT OF THE BOX

  After byte-comparing retail reference packages against the HomebrewTest
  build, and cross-referencing the SvenGDK LibProsperoPkg ps5-pkg-format
  spec, two more defaults were misaligned for retail content. Both are
  now fixed in ffpfsc-pkg-tool with safe fallbacks:

  • AUTO-FAKE-SIGN raw ELFs in the source (default ON).
    LibProsperoPkg's own ProsperoFself.MakeFself converts each raw ELF
    (eboot.bin, *.elf, *.prx, *.sprx) to a fake-self before packing.
    Idempotent — already-SELF files and non-ELF files are skipped.
    Original source folder is never modified: a hardlink mirror of the
    source is created in --temp-dir, only the ELFs to convert are
    unlinked and rewritten in the mirror, and the mirror is deleted
    after the build. Opt out with the new --no-fake-sign flag if the
    source ships pre-signed and you want exact byte-preservation.

    Why this matters: retail game dumps carry unsigned ELFs. A PS5's
    debug-image loader kills any package whose eboot is not fake-self
    (short fan-spin, then CE-100096-6). Users had to run the separate
    🖊 Sign job before Pack; now the builder handles it in-process.

  • AUTO-DETECT PlayGoChunkCount from the source's sce_sys/playgo-chunk.dat.
    If the source (a real game dump) declares a specific chunk count in
    its own PlayGo table, the builder now respects that instead of
    forcing the 1-chunk default set for HomebrewTest-scale content.
    The --playgo-chunks N override still wins if the user pins it.

    Log lines make the choice visible:
        [playgo] source declares 5 chunk(s); using that (was default 1)
        [sign]   fake-signed 6 ELF(s); skipped 2 (already-SELF, non-ELF, or errors)

  • Single unified staging pass. The DDS-icon generation from 1.1.7,
    the new fake-sign pass, and any future source pre-processing all
    share ONE mirror in --temp-dir instead of stacking them, so a
    100 GB game gets exactly one hardlink walk rather than N.

  Verified: 92/92 pipeline tests pass, HomebrewTest builds byte-identically
  to 1.1.10 (nothing regressed on a small homebrew whose eboot is already
  fake-signed). Retail acceptance on the console followed in 1.1.12.

fPKG BUILDS FINALLY LAUNCH ON 11.60 (kstuff-lite 1.13+)

  • Root cause found: LibProsperoPkg 1.2.0's built-in Kraken encoder
    produces byte-identical output to Sony's Publishing Tools DLL — no
    Wine needed, no DLL reversing. The whole "≤ 11.40 only" story was
    a single wrong flag in our builder.

    LibProsperoPkg defaults to a random-seed AES-XTS wrap on the outer
    PFS. The PS5 debug loader accepts only the plaintext-no-auth mode
    (outer PFS marked encrypted, seed set to the sentinel value
    "PPPLAIN-NOAUTH!", no actual wrap). Sony's DLL always uses that
    mode for debug images. Ours didn't — validated structurally,
    extract-inner worked, but the console rejected it at launch with
    CE-100096-6.

    Program.cs now sets ProsperoPublisherImageMode.PlaintextNoAuth and
    PlayGoChunkCount = 1 (Sony's default; LibProsperoPkg's was 64).
    Both fixes verified against a libScePubTools.dll reference build:
    inner PFS byte-identical; outer PFS wrap differs only in harmless
    timestamp/ICV bytes.

  • pfs-dump (scratch tool, not shipped): opens a fPKG, decrypts the
    outer PFS, dumps three layers (A = outer decrypted, B = stored
    pfs_image.dat, C = fully NAPS-decompressed inner PFS) so future
    debugging can byte-diff a builder's output against a reference at
    each level of the container.

  • --playgo-chunks NEW build flag (integer 1..255) — overrides the
    new default of 1 for advanced PlayGo layouts.

  • Firmware note in the Pack dialog, the fPKG-tool README and the
    top-level README updated: no more "≤ 11.40 only". The ceiling on
    any given firmware is the jailbreak stack, not the builder.

  • Verified on-console 2026-09-24: retail PS5 on FW 11.60 with
    kstuff-lite 1.13-dr-test3 launches the HomebrewTest fPKG built by
    this tool.

COPY JOB FIXES — the 1.1.8 copy op reported failure after succeeding

  • A successful copy raised "Compression Failed — Backend exited but no
    new .ffpfsc output was created". The copy op fell through to the PACK
    completion path, which scans the output folder for a newly-created
    .ffpfsc. A copy's file lands synchronously at the exact name the
    backend was told to use, so there is nothing to discover. Copy now
    short-circuits on a clean exit like fake-sign does, and skips the
    bundle-siblings copy and the ShadowMount sniff (neither applies to a
    straight file transport).

  • Copy jobs no longer land in the compression history (they move an
    existing package, they do not produce a new one), and no longer arm
    the OOM auto-retry (there is no memory-hungry pass to retry).

  • Exit 2 (source == destination) and exit 3 (a different file already
    owns that name) are deliberate skips, not failures. They now report
    "Copy skipped — <reason>. Nothing was changed." instead of the
    failure dialog.

  • The error dialog is job-aware. "Compression Failed" with MkPFS and
    temp-space causes made no sense for a copy, an extraction or a
    fake-sign, so the title and the Possible Causes list now match the
    job that actually failed.

  • Startup leftover sweep widened: it also scans every output folder
    recorded in the history (and its parent), so orphaned _ffpfsc_temp /
    _extracted folders on drives used in earlier sessions get surfaced
    instead of accumulating silently. Prompt threshold lowered from
    1 GiB to 64 MiB.

  • 8 new regression tests drive a real copy job through CLIWorker end to
    end (88 GUI tests total, all green).

COPY / ORGANIZE — SAME-FORMAT JOBS SKIP THE ENCODER

  • The Pack dialog now recognises when a source is already in the target
    format (.ffpfsc → .ffpfsc, .ffpfs → .ffpfs, .pkg → .pkg) and routes
    it through a straight file copy instead of re-encoding. Same drive
    (matching st_dev) → os.rename, atomic and instant regardless of file
    size. Different drive → chunked copy via a *.copy-tmp file with
    os.replace on success (no half-written target visible under the
    final name); the source is deleted afterwards unless the new
    "Delete source after successful copy" checkbox is unchecked.
    Setting persists as copy_delete_source in settings.json.

  • New "🗂 Organize" button in the job bar: pick a source folder and a
    destination root; the app walks recursively for .ffpfsc / .ffpfs /
    .pkg, deduplicates by resolved path (symlink-safe), and enqueues one
    copy job per file. Each job runs the same auto-organize naming as a
    fresh build (‹Title [TID] [vX.Y.Z]›/‹Title [TID] [vX.Y]› derived
    from the source's own param.json — read out of the CNT for a .pkg
    or the inner PFS for a .ffpfsc/.ffpfs, no full decode).

  • The queue shows COPY jobs with their own badge and detail line
    ("<size> · move (or copy+delete)" / "copy (keep src)").

  • Two safety rails on every copy: a src → dst that resolves to the
    same file skips (exit 2, source kept); a dst already occupied by a
    different file skips (exit 3, both kept intact — never overwritten,
    never renamed to (2)).

  • backend/copy_job.py + backend/tests/test_copy_job.py (10 tests) +
    backend/tests/test_organize_walk.py (5 tests); cli.py gains --copy,
    --copy-name and --keep-source.

fPKG BUILDS THE CONSOLE ACTUALLY LAUNCHES  (on ≤ 11.40)

  • The tool now auto-generates the sce_sys/icon0.dds CNT entry, the
    piece the PS5 kernel needs to start the app. Before this an fPKG
    installed but never launched (missing 262 KB DDS icon0 entry ->
    CE-100096-6). LibProsperoPkg 1.2.0's builder moves any sce_sys/*.dds
    into the outer CNT (see ProsperoPfsLayoutOptions.FilterOuterPackage-
    Entries) but does NOT generate the DDS itself; the a53 reference GUI
    calls ProsperoDdsEncoder.EncodePngToDds up front, and so do we now
    (the encoder's own API). Magick.NET is back in the bundled build (it
    is what LibProsperoPkg uses under the hood) and re-signed ad-hoc so
    Gatekeeper does not block the extracted native dylib. Our own build
    is now structurally equivalent to the a53 GUI's output (13 CNT
    entries, identical inner tree, 262,292 B DDS icon, identical DRM /
    eboot magic; the only bit-level difference is the random per-package
    seed and content-agnostic playgo chunk count).

  • FIRMWARE REALITY, SAID CLEARLY
    fPKG install-and-launch works on jailbroken PS5 firmware ≤ 11.40.
    Sony patched the install path with system software 11.50 — packages
    built by ANY tool (this one, the a53 GUI, verified reference
    packages that launch elsewhere) install but fail with CE-100096-6 on
    11.60. The dialog and README say so, so nobody chases their tail on
    a modern firmware.

  • ffpfsc-pkg-tool is 51.6 MB again (was 24 MB without Magick.NET) —
    same speed on the Kraken/AES path. Trimming is off because Magick's
    Prospero-facing path is reflection-driven and would be pruned.
    A DllImportResolver installed in Main() walks the single-file
    extraction cache to load the Magick native dylib regardless of
    where .NET drops it. PKG_TOOL_TRACE=1 prints the resolver decisions.

BROWSE A .pkg LIKE A .ffpfsc

  • The PFS browser (🔎 Browse) opens an fPKG too: list its contents and
    pull out single files or folders — without unpacking the package. The
    tool got two commands for that, list-inner and extract-inner --members,
    built on random access into the inner image: outer-PFS AES-XTS decrypt
    per 64 KiB block → NAPS layout → block-cached inner PFS reader. The
    library's own DecodePlaintextInnerPfsRange refuses our (encrypted)
    packages, and its superblock scan would have decoded the whole image
    (our images are data-first), so both are done from public building
    blocks with a probe of the last NAPS file. Measured on a 242 MB
    package: listing 0.12 s reading 1.5 MiB; a 47 MB selection 0.2 s at
    88 MB RSS, SHA-identical to the full extract. sce_sys metadata from the
    CNT (param.json, icons, playgo-*) appears in the tree and is selectable
    like any file. The backend routes --list-image / --extract-from for a
    .pkg to the tool, answering in the browser's own JSON and progress
    format — the dialog itself only learned the file type.
  • Tool fix found on the way: inspect --json / validate --json / extract-inner
    --json had been broken since the 1.1.1 trimming (reflection JSON is
    disabled in a trimmed build) — now source-generated.
  • Harness: 60 → 92 checks (list/select parity, sizes, CNT selection,
    progress, empty dirs, unknown member, the three --json commands);
    GUI driver 78 (backend routing for .pkg + the dialog listing).

AUTO-ORGANIZE — THROW ANYTHING IN, GET A LIBRARY OUT

  • New switch in the Pack dialog (remembered, per job, default ON, also
    applied to dropped / browsed sources): "Auto-organize". Every pack and
    fPKG job then lands as
        <Output>/<Title> [TITLEID] [vXX.YYY.ZZZ]/<Title> [TITLEID] [vXX.YYY].ffpfsc
    (or .pkg), named from the GAME's own sce_sys/param.json — whatever the
    archive, folder or image was called. Folder = full version, file =
    short version, both with the 'v'; ™®© are dropped and "A: B" becomes
    "A - B". Bundle extras (DLC archives, unlockers, nfo) are copied into
    that folder as before. The ShadowMount 63-byte cap still applies to the
    file name (edition suffix trimmed first, tags always kept).
      - folder source: param.json read directly;
      - archive: read after extraction, right before packing;
      - .ffpfs/.ffpfsc: the single member sce_sys/param.json is pulled via the
        browse path (MkPFS's generic metadata reader cannot follow our nested
        image layout — it reported "missing exFAT signature");
      - .exfat/.ffpkg: MkPFS's exFAT metadata reader;
      - nothing readable → today's naming, one WARN in the log.
    fPKG: the tool still writes '<content-id>-A…-V….pkg'; the worker renames
    it to the library name right after the build (assumption, not yet
    verified on a console: installers read the header, not the file name).

  • BUNDLE OUTPUT NEVER LANDS INSIDE THE SOURCE FOLDER ANY MORE
    A folder holding one archive mirrored its own name at the destination —
    and when the destination was the folder's parent, that "mirror" WAS the
    source folder, so the .ffpfsc / .pkg ended up next to the archive, named
    after the folder ("convert [PPSA00003] [01.003].ffpfsc"). With
    auto-organize off, such a job now writes to the chosen output folder;
    mirroring elsewhere (a library drive) is unchanged.

  • AMPR: GAMES THAT SHIP THEIR OWN EMU FILES ARE RECOGNISED
    A PlayGo release that already carries fakelib/libSceAmpr.sprx +
    libScePlayGo.sprx (and usually ampr_emu.index) no longer triggers the
    "AMPR emu folder not set" prompt: nothing is asked, nothing injected;
    a shipped index is kept as-is (it belongs to those .sprx), a missing
    one is built. Only one of the two shipped → the emu folder supplies the
    other. Fake-sign-before-pack is skipped (WARN) for a DIRECT folder that
    ships an index — signing would make it stale, and we never rewrite your
    library.

  • GUI driver: 74 checks (auto-organize names for folder / image / fPKG,
    pkg rename, title cleanup, mirror guard, dialog checkbox, snapshot,
    AMPR shipped-files detection).

fPKG IS THE PACK DIALOG'S THIRD FORMAT — ANY SOURCE → .pkg

  • ONE DOOR
      The Pack dialog's format switch became a three-way choice:
      .ffpfsc (compressed) | .ffpfs (uncompressed) | .pkg (fPKG). Picking
      .pkg unfolds the fPKG block (identity + inner codec / Kraken backend /
      level) below the format row; the dialog grows to 700x840 and shrinks
      back when you switch away. The separate "⇢fPKG" button and the
      Build-fPKG dialog are gone; the Converter's "Build fPKG" step and a
      double-click on a queued fPKG job open the Pack dialog with .pkg
      pre-selected.

  • THE INPUT NO LONGER MATTERS
      With .pkg selected every pack source becomes an fPKG job: a game
      folder, a parent folder (scanned — each game its own .pkg), a library
      of bundles (folder mirrored, DLC extras copied next to the .pkg), a
      third-party archive (extracted on its turn, multi-game archives included),
      a .exfat/.ffpkg disk image, a .ffpfs — and a .ffpfsc, which the other
      two formats refuse because it is already packed. The queue snapshot
      that used to stamp compressed/uncompressed onto a fresh pack item now
      turns it into an fPKG job when .pkg is the remembered format — so a
      dropped or browsed source follows the last chosen format, as before.

  • IDENTITY: param.json DECIDES  (fixes a real 1.1.0 defect)
      The bundled tool stamps the header with --content-id as given and
      never reconciles it with sce_sys/param.json; the image→fPKG path
      guessed "UP9000-<TID>_00-PROSPERO00000000", so every real game image
      produced a package whose header disagreed with its own param.json
      ("[FAIL] param.contentId ... != CNT header" in validate). Now the
      backend reads param.json of the resolved source (folder, unwrapped
      image, extracted archive alike) and takes content id, title id,
      version and title from there; --content-id & co. are fallbacks for
      what it lacks and are no longer required. A disagreeing argument is
      logged as a WARN and ignored. The dialog pre-fills the identity from
      param.json for a game folder (dropped again when the source changes)
      and leaves it empty — "auto" — for archives and images.

  • ALSO
      fPKG jobs skip the AMPR/APR emu injection (a .pkg installs natively);
      an fPKG job survives archive extraction as an fPKG job (the payload
      copy used to reset it to pack/unpack); the extra games of a multi-game
      archive become fPKG jobs sharing the compression settings only (never
      the first game's identity); a scan-detected patch is dropped with a
      WARN when a bundle becomes an fPKG job (the builder has no patch
      overlay); bundle sub-folders apply to .pkg output and bundle extras
      are copied next to it; identity typed for an archive source rides
      along as the fallback; editing pack ↔ fPKG on the same source converts
      in place (bundle tags, archive password and queue position survive);
      the space gate lets fPKG extract through and sizes a .ffpfsc source
      at 2x for the unwrap; the remembered fPKG compression (inner/backend/
      speed) persists as fpkg_defaults, the remembered format as
      output_format (the old output_compressed bool stays in sync for the
      pack pipeline).

  • THE fPKG TOOL: 53 MB → 25 MB, SAME SPEED
      backend/native/ffpfsc-pkg-tool is rebuilt without Magick.NET and with
      the .NET runtime trimmed. LibProsperoPkg only references ImageMagick
      for icon conversion; none of our code paths (build in all three
      codec layers, extract, validate, deterministic build) ever load it —
      the 57-check harness passes without it, and it was 28 MB of the file.
      Measured on 240 MB of mixed data the slim JIT build runs at the same
      throughput as before (34 vs 33 MB/s). NativeAOT variants were tried
      too (16-18 MB) and rejected: 10-23 % slower on the Kraken/AES path.
      The wrapper's source (Program.cs, PkgTool.csproj, build README) now
      lives in backend/native/src/ffpfsc-pkg-tool/ — it existed only in a
      temp folder before, and GPL-3 wants it next to the binary. The first
      fPKG attempt's leftovers (prospero.py, libprosperopkg.dylib/.h,
      patches/) are deleted; nothing used them and they shipped as 7 MB of
      dead weight in the app.

  • TWO 1.1.0 CLAIMS CORRECTED (measured, not assumed)
      "Inner codec none = files stored raw" was wrong: the tool Kraken-packs
      every file in every mode (a compressible 8 MB file came out as 1.2 MB
      with 'none'; only incompressible data is stored). --mode adds a codec
      LAYER over the whole inner image; on already-packed data all three
      layers gave the same package size. Texts in the dialog, README, CLI
      help and fpkg.py say so now.
      "Level 0-9" was a placebo: the level reaches the encoder (the log
      says so), but 0..9 produce byte-identical output; only -4..-1 switch
      to a faster, slightly weaker preset (40 MB mixed data: about a quarter
      less time, ~8 % larger). The slider is gone; the dialog offers
      "Kraken speed: normal | fast" (level 7 / -4). The tuning-bar note for
      an fPKG job says none of its controls apply.

  • TESTS
      CLI harness: +1 test, 6 checks (param.json beats a disagreeing
      --content-id and validate stays green; ids omitted → builds; no
      param.json and no ids → readable refusal) — 57/57. GUI driver
      rewritten for the unified dialog: pre-fill, optional identity for
      images/archives, add via the shared classifier, edit, pack↔fPKG
      switch, archive placeholder kept as fPKG, remembered-format drop,
      dialog sizing — 40/40.

fPKG IS NOW A FIRST-CLASS PIPELINE (this is why it's 1.1.0)

  • ONE-CLICK  .ffpfsc / .ffpfs / .exfat / .ffpkg  →  fPKG
      Converter dialog got a "Build fPKG" step next to Decompress/Unpack,
      and the Build-fPKG dialog accepts an image as source. The backend
      unwraps the image on the TEMP drive (mkpfs unpack + nested unwrap,
      exFAT read), builds the .pkg, validates it, removes the scratch.
        --fpkg-build <image>  --temp-dir <fast drive>  --compression-level N

  • REAL Build-fPKG DIALOG  (was a bare prompt)
      Same look as Pack: source File…/Folder…, output folder, identity
      grid (Content ID / Title ID / Title / Version — auto-filled from
      sce_sys/param.json for a folder, from the file name for an image,
      validated against the console's id patterns), inner codec
      none/zlib/kraken, Kraken backend builtin/publishingtools, its own
      Level slider (maps to LibProsperoPkg Kraken -4..9 / zlib 0..9).
      Explains why CPU cores + block size from the tuning bar don't apply.

  • TUNING-BAR SEMANTICS MADE HONEST
      Level → forwarded per job (--compression-level → --level).
      CPU cores → pinned to 1 for fPKG (LibProsperoPkg 1.2.0 outer-PFS race).
      Block size → not applicable (format-fixed 64 KiB / 256 KiB).
      Temp drive → forwarded (--temp-dir → LibProsperoPkg TemporaryDirectory);
      the placement router's chosen build drive is used, like for packs.

  • WORKER / PROGRESS
      New stage weight tables for fPKG build and extract; the backend now
      emits [PHASE] markers + progress bars (source scan → unwrap → inner
      image % → outer-PFS AES-XTS % → finalize % → validate) so the bar
      moves instead of sitting on "Scanning 0%". Progress bars are locked
      to the announced phase for fPKG jobs (no keyword guessing).
      Output detection knows .pkg (build) and the /app0 folder (extract) —
      previously a successful build was reported as "no .ffpfsc created".
      ShadowMount checks, bundle copying and the mkpfs OOM core-step-down
      no longer run for fPKG jobs. Success messages name the job type.

  • QUEUE / EDITING / SETTINGS
      Double-click edits fPKG jobs (Build dialog in edit mode; the mini
      dialog for Extract). Queue badges fPKG-EX / fPKG-BD, details mode.
      Settings → Folders: optional "fPKG — Publishing Tools DLL" path
      (your own copy, never bundled) feeding the publishingtools backend.
      History skips fPKG extracts (no compression to rate); fPKG builds
      record the real source size so the ratio is meaningful.
      Pack dialog refuses .pkg / .ffpfsc with a pointer to the right job.
      Visual pass (window-capture verified): Build-fPKG dialog resized so
      its Cancel / Add-to-queue row is visible; Extract mini dialog taller
      for its two rows; Converter widened for the fourth (fPKG) node; a
      .pkg queue row shows its title id (PPSA…) instead of "Unknown"; the
      tuning bar shows which controls the selected fPKG job honours; the
      header caption mentions .pkg. Backend phase order no longer jumps
      back (Reading Game → Creating Temp PFS → Compressing → Writing).

DIAGNOSTIC VALIDATOR

  ffpfsc-pkg-tool validate <pkg>            (also --fpkg-validate <pkg> in cli.py)

  17-point checklist that answers "why does the console reject this?":
    file / FIH magic / CNT header / content-id format / signed-byte /
    PFS bounds / embedded-CNT bounds / NAPS layout size / CNT signature
    wrap / required entries (param.json, icon0.png, playgo-chunk.dat) /
    param.contentId matches header / applicationDrmType / inner-PFS
    decodes / eboot.bin has the expected fake-self magic.

  The CLI now AUTO-RUNS the validator right after every successful
  --fpkg-build so a broken package is flagged in the log before it
  ever leaves the mac.

CNT METADATA MERGE ON EXTRACT

  Fixed: extract-inner used to lose sce_sys/param.json, sce_sys/icon0.png,
  and the playgo-*.dat entries (they live in the CNT container, not in
  the inner PFS). Chain 3 (fPKG → mkpfs pack) would then fail because
  mkpfs requires param.json. The extractor now merges the CNT metadata
  into sce_sys/ automatically; --no-merge-cnt keeps the old behaviour.

NEW: fPKG BUILD AND EXTRACT (native macOS, no external DLL)

  Two new queue operations sit next to Pack / Convert / Patch / Sign in
  the "Add job" bar:

    📥  fPKG⇢     Extract an installable PS5 fake package (.pkg) into a
                   /app0-style folder.
    📦  ⇢fPKG    Build a debug fPKG from a prepared /app0 folder.

  Runs entirely on macOS. No Wine, no Windows, no external DLL required.
  Powered by a bundled self-contained .NET 9 CLI (`ffpfsc-pkg-tool`, GPL-3,
  ~53 MB under backend/native/) that wraps drakmor's LibProsperoPkg 1.2.0
  from the a53-fpkg 0.5 release.

  BUILD OPTIONS

    Kraken backend      builtin (default, no DLL) / automatic /
                         publishingtools (requires the leaked Sony
                         libScePubTools.dll at the given path) /
                         uncompressed.
    Inner codec         none (safest, largest) / zlib / kraken.
    Content ID / Title  filled from sce_sys/param.json if present, else
                         asked for in the dialog.

  ROUND-TRIP VERIFIED locally on the HomebrewTest sample: build then
  extract-inner returns every source file byte-identical (fake-sign
  transforms eboot.bin as expected). On-console install is the user's
  test and depends on kstuff-fpkg support on his firmware.

  BACKEND CLI

    backend/cli.py picked up matching flags so the app and shell users
    both hit the same code path:

      --fpkg-extract PKG               (with OUTPUT = target folder)
      --fpkg-build   SRC-DIR           (with OUTPUT = folder for the .pkg)
        --content-id, --title-id, --fpkg-title, --fpkg-version
        --fpkg-inner {none,zlib,kraken}
        --fpkg-kraken-backend {automatic,builtin,publishingtools,uncompressed}
        --fpkg-pubtools-dll PATH

  RACE FIX applied at our layer

    LibProsperoPkg 1.2.0's outer-PFS worker crashes with SIGSEGV in
    ProsperoOuterPfsSignature.BlockSector when its build path runs
    encryption across multiple threads. Our wrapper forces
    KrakenMaxDegreeOfParallelism = 1 (also gates the outer-PFS pool)
    so 8/8 test runs succeed instead of 4/8.

BUNDLED THIRD-PARTY CODE (GPL scope)

  ffpfsc-pkg-tool statically bundles LibProsperoPkg (GPL-3-or-later),
  BCnEncoder.NET (MIT), CommunityToolkit.HighPerformance (MIT), and
  Magick.NET-Q8-AnyCPU (Apache-2.0). The rest of ps5-ffpfsc-ultra
  is unchanged; the GPL scope covers the native fPKG tool only.
